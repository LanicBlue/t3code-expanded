审计的 priority 是按"一旦触发的严重度"排的；**触发条件是另一根轴**，两者交叉才是真实优先级：

- **① 常驻必然**：现在每次运行都在发生（性能税 / 功能不生效 / 能力缺失），单项痛感小但持续。
- **② 特定事件触发、但当前运行形态下命中只是时间问题**：cron 持续产活 + 开发期频繁重启的组合。
  无自愈、命中即静默。**无人值守闭环目标下这是必修档**。

  形态（静默全黑）爆发。本 fork 重 vendor 频率高，该窗口在开发节奏里常见。
- **④ 基本碰不上 / 与当前形态低相关**：可以不管，留着备忘。

当时结论一句话：没有一个发现是"现在就在错误地运行"。近期目标若是让 cron→agent 闭环真正无人值守，
先修 ②；若只是开发期交互使用，①里最划算的是 WAL 一行 + listSessions N+1。

#### 2. [HIGH | 工作量 M] Delivery is purely event-driven with no reconciliation: acked-notice work strands forever after a t3 restart (and after deferred flush failures on an otherwise-idle thread)

- **维度**: PS 集成面（projectService/ + MCP 工具 + vendored SDK）
- **位置**: projectService/ProjectConsumerRuntimeService + ProjectWorkNoticeRouting
- **触发条件**: ② cron 持续产活 + 开发期频繁重启的组合下命中只是时间问题；一旦命中永久静默、无自愈
- **证据**: The router is driven only by SDK notices and engine thread events (ProjectConsumerRuntimeService.ts:603-609); its session registry is in-memory (ProjectWorkNoticeRouting.ts:389 sessionsRef) and onStateChange('connected') only updates statusRef (ProjectConsumerRuntimeService.ts:270-283) — nothing re-lists work. The restart test covers only a still-PENDING notice replay (ProjectConsumerRuntimeService.test.ts:904-930); a notice that was ACKed before restart is never re-emitted by Project Service, so open work has no driver afterwards. The deferred-failure path has the same shape: ProjectWorkNoticeRouting.ts:782-787 keeps pendingWork=true and explicitly waits for 'the next thread event or wake' — if the thread is otherwise idle and no new notice arrives, there is no next event. A wedged latestTurn.state==='running' also keeps isWorkThreadBusy true forever (ProjectWorkNoticeRouting.ts:184-187), so pendingWork never flushes.
- **影响**: Routine t3 restarts/crashes between notification and submit strand the work silently: the pre-restart thread survives in the projection but nothing ever notifies it again (router state lost, SDK dedup memory lost, PS will not re-fire the acked notice) until an unrelated NEW notice happens to arrive for the same (agentId, projectId). For an unattended work-dispatch loop this is a silent liveness hole; the only current recovery is luck or manual action.
- **修法**: Add a gentle reconciliation sweep: on runtime state->connected and on a long interval (e.g., every few minutes), for each Project-enabled logical agent x PS project (via listProjects + listMy), if open work exists but no session is in 'notifying' phase for the head the agent was last told about, route a synthetic wake (reusing routeWake's serialization). Reuses the existing at-delivery-time authoritative query, so no new state is introduced.
- **对抗核实**: real=True —— CONFIRMED after adversarial review; every citation checks out and no missed handling exists. (1) ProjectConsumerRuntimeService.ts:603-609 wires only engine thread events into the router; notices arrive only via SDK wakeAgent (adapter at 222-247). Router state is in-memory (ProjectWorkNoticeRouting.ts:389 sessionsRef) and onStateChange('connected') only writes statusRef (270-283). (2) SDK 0.10.0 (vendored tarball, extracted read-only to /tmp) ACKs a notice only after wakeAgent resolves; reconnect replay covers only unacked server inventory; dedup memory is process-local — so an ACKed notice is never re-fired. Router comments themselves assert this (ProjectWorkNoticeRouting.ts:781-784). (3) No reconciliation anywhere: no Schedule/interval in projectService; listOpenAssignedWork is callable only inside routing passes entered via routeWake/onThreadEvent; onThreadEvent (922-935) iterates the empty post-restart map, so even a surviving thread's events drive nothing; ProviderCommandReactor.ts:1407-1409 explicitly says pre-start turn work 'cannot be resumed' (hot stream), and no startup sweep marks orphaned running turns. (4) Restart test (ProjectConsumerRuntimeService.test.ts:904-945) covers only the still-PENDING notice replay. (5) Impact is real and wider than a narrow crash window: the busy-session coalesce path (838-841) ACKs notices while only recording pendingWork=true in memory, so ANY t3 restart while an agent turn is running strands the current run plus every queued run behind it — the whole unattended dispatch loop stalls silently until a new unrelated notice for the same (agentId, projectId) or manual action. The deferred-failure path (776-795, keeps pendingWork, waits for 'next thread event or wake' that never comes on an idle thread) and isWorkThreadBusy's unconditional latestTurn.state==='running' (184-187) are confirmed as stated, though they are secondary triggers. Not data loss — work stays open in PS — but a silent liveness hole in the fork's core feature (unattended PS→agent work dispatch), so high stands. Fix (effort M): on 'connected'/'start', one reconciliation pass per project-enabled agent: list open assigned work per known PS project and route it (create a fresh session; do not reuse the dead pre-restart thread whose queued/running turn is unrecoverable; seed lastDeliveredHeadRunId=null on the new session to preserve the no-nag invariant).

- **证据**: apps/server/src/provider/Layers/ProviderService.ts:1096-1113 — listSessions() calls directory.listThreadIds() (which itself runs repository.list(), fetching and decoding ALL rows, ProviderSessionDirectory.ts:167-171) then re-fetches each row individually via directory.getBinding(threadId) → repository.getByThreadId (one SELECT per thread). Callers on hot paths: ProviderCommandReactor.ts:484-489 ensureSessionForThread → resolveActiveSession → providerService.listSessions() on EVERY thread.turn.start (via buildSendTurnRequestForThread, ProviderCommandReactor.ts:738); CheckpointReactor.ts:155-163 resolveSessionRuntimeForThread → listSessions(), invoked from resolveCheckpointCwd (CheckpointReactor.ts:192 — computed even when preferSessionRuntime=false) on every turn.started, turn.completed, placeholder-capture, and every user message/turn-start-requested domain event. Delete the provider_session_runtime row on thread deletion and prune stopped rows older than the resume window (or cap them). Optionally cache bindings keyed by a version bumped on upsert.

(3) Growth confirmed: stopSession only upserts status=stopped (ProviderService.ts:1058-1066); ThreadDeletionReactor.ts:45-50 and ProviderSessionReaper.ts:87 only stop; deleteByThreadId (persistence/ProviderSessionRuntime.ts:311-323) has zero production callers (repo-wide grep). (4) No missed mitigation: no cache anywhere in front of listSessions/directory; hasHandledTurnStartRecently (ProviderCommandReactor.ts:92-93,1063-1066) only dedups duplicate processing of the same event. WHY MEDIUM NOT HIGH: node:sqlite point lookups on thread_id PRIMARY KEY are in-process and microsecond-scale; payloads are small (cwd/model/activeTurnId/selection). #### 4. [MEDIUM | 工作量 M] refreshThreadShellSummary rescans the entire thread (all message texts) on every hot event, inside the serialized command worker

- **维度**: 会话运行时 + 持久化（orchestration/persistence/sqlite）
- **位置**: persistence/projection-pipeline
- **触发条件**: ① 常驻——每条消息事件都在付，随会话长度恶化
- **证据**: apps/server/src/orchestration/Layers/ProjectionPipeline.ts:854-871 — every thread.message-sent (including each streaming spill/legacy token delta, decider.ts:1231-1256 maps thread.message.assistant.delta → thread.message-sent with streaming=true), activity-appended, session-set, turn-diff-completed, and proposed-plan-upserted event triggers refreshThreadShellSummary. All of this runs on the single engine worker fiber (OrchestrationEngine.ts:323-324), so every queued command waits behind it.
- **影响**: O(thread size) work per event → O(n²) cumulative per thread. On a long conversation with an active agent turn (frequent activities + assistant spills), each event re-decodes every prior message's full text through Schema.fromJsonString, blocks the command queue, and inflates turn latency and UI event lag; also write-amplifies the threads row and WAL.
- **修法**: Skip the refresh when event.payload.streaming === true for role=assistant (none of pendingApprovalCount/pendingUserInputCount/hasActionableProposedPlan/latestUserMessageAt can change on a delta). All of it runs on the single command worker (OrchestrationEngine.ts:323-324) and in fact INSIDE the command append transaction (OrchestrationEngine.ts:195), with all 9 projectors sequential (ProjectionPipeline.ts:1698-1709) — so every queued dispatch waits behind it; threads row is written twice per event (26 cols). #### 5. [MEDIUM | 工作量 M] No real provider-session heartbeat: last_seen_at freezes at turn start and no watchdog detects a wedged turn

- **维度**: 会话运行时 + 持久化（orchestration/persistence/sqlite）
- **位置**: liveness/session-lifecycle
- **触发条件**: ① 常驻缺失——turn 卡死时才痛
- **证据**: provider_session_runtime.last_seen_at is written only by directory.upsert at session start/sendTurn/respond/stop (ProviderService.ts:411, 884, 1058, 1247); ProviderRuntimeIngestion never touches it. The only consumer is ProviderSessionReaper.ts:42-110, which (a) skips any thread with session.activeTurnId != null (line 65) or in-memory backgroundLiveness (line 78), and (b) reaps purely on 30-min idle. There is no stall detector anywhere (grep for watchdog/stall/hung-turn in orchestration/ and provider/ finds nothing). Process death is handled only when the adapter's exitCode fiber fires (CodexSessionRuntime.ts:1720-1745); a hung/killed-without-exit-event provider leaves status=running + activeTurnId set indefinitely.
- **影响**: A wedged provider process (network hang, SIGKILL of the CLI, deadlock) shows the thread as running forever, the turn never settles, checkpoint capture for that turn never runs, and the reaper explicitly refuses to act. The only recovery is a full server restart, at which point reconcileProviderSessions (serverRuntimeStartup.ts:300-378) error-settles it as an orphan. last_seen_at is also structurally misleading for any diagnostics that treat it as liveness.
- **修法**: Two pieces: (1) make last_seen_at a real liveness signal — throttle-update it (e.g. ≥60s interval) on every ingested provider runtime event in ProviderRuntimeIngestion, cheap single-row UPDATE; (2) add a stall watchdog to the existing reaper sweep: if session.status==running and no runtime event/last_seen bump for > threshold (say 10-15 min, configurable), probe adapter health, then interrupt the turn and settle session to error/interrupted with a user-visible activity, mirroring the orphan-reconciliation event. Give in-memory ThreadBackgroundLiveness a TTL so quiet-but-registered background work can't pin liveness forever.
- **对抗核实**: real=True（原始优先级 high 被核实者修正） —— VERIFIED with citations checked. (1) last_seen_at is written only by ProviderSessionDirectory.upsert (ProviderSessionDirectory.ts:138); sole upsert callers are ProviderService.ts:411/884/1058/1247 and serverRuntimeStartup.ts:328 — never during a running turn. (2) ProviderRuntimeIngestion.ts has zero references to the directory/lastSeenAt. (3) ProviderSessionReaper.ts:17 (30-min idle), :65 skips activeTurnId, :78 skips backgroundLiveness — its own comment (74-77) admits 'nothing bumps lastSeenAt between turns'. (4) No watchdog/stall/turn-timeout anywhere in orchestration/ or provider/; runOpenCodeSdk (opencodeRuntime.ts:96) has no timeout. (5) CodexSessionRuntime.ts:~1720-1745 exitCode fiber and OpenCodeAdapter.ts:~1476/~1486 watchers handle process death; reconcileProviderSessions (serverRuntimeStartup.ts:300-378) error-settles orphans only at restart. (6) CheckpointReactor.ts:356/871 keys on turn.completed, so a wedged turn never checkpoints. IMPACT REAL but narrower than claimed: 'only recovery is a full server restart' is overstated — process death (incl. SIGKILL of a direct child) fires exit watchers → session.exited → ingestion settles the turn (ProviderRuntimeIngestion.ts:1597-1601 clears activeTurnId); and if the provider control plane still answers, interruptTurn settles locally (OpenCodeAdapter.ts:1876-1904 emits turn.aborted after session.abort) and stopSession tears down locally (stopOpenCodeContext, OpenCodeAdapter.ts:686-708). The restart-only case is provider alive AND control plane unresponsive — plausible (Codex parent turn/interrupt at CodexSessionRuntime.ts:1899-1901 is unbounded, unlike its bounded children at 1885-1893; OpenCode abort is awaited unbounded before Scope.close). For this fork's autonomous PS→ASC dispatch loop a silent indefinite wedge is a genuine availability gap the reaper explicitly refuses to clean, but there is no data loss (restart reconcile error-settles), common hangs are manually recoverable via interrupt/stop, and death cases are already handled — resilience, not correctness/data risk. FIX SKETCH: (a) record lastEventAt from ingested runtime events (or bump directory lastSeenAt in ingestion) and add a stall watchdog: activeTurnId set + no events for N min (respecting backgroundLiveness progress) → attempt interruptTurn with a bounded request, then error-settle/stopSession; (b) bound the unbounded abort/interrupt requests (3-10s timeouts as already done for Codex children). Effort M.
